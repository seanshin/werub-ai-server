# 모델 서빙 구성 설계 참고 — VRAM·상주 정책·적재 비용 (실측 기준선)

> 최초 작성 2026-07-30(v2.124.61) · 대상 GPU 서버(RTX 5080 16GB / RAM 31GB / NVMe)
> 목적: **앞으로 AI 서버를 구성·증설·재설계할 때 추측 대신 이 수치에서 출발**하기 위한 문서.
> 여기 숫자는 전부 이 서버에서 직접 잰 값이다. 추정치는 추정이라고 표시했다.

## 1. 하드웨어 기준선 (실측)

| 항목 | 값 | 측정 방법 |
|------|-----|-----------|
| GPU VRAM | **16.3 GB**(RTX 5080) | `nvidia-smi` |
| 시스템 RAM | **31.2 GB**(유휴 시 파일 캐시 ~27GB) | `free -m` |
| 스왑 | 7 GB(사용 0) | `free -m` |
| **디스크 순차 읽기(버퍼드)** | **9.9 GB/s** | 35GB 콜드 읽기 실측(2026-08-03) — `posix_fadvise(DONTNEED)`로 캐시 축출 후 |
| 디스크 순차 읽기(O_DIRECT) | 3.1 GB/s | `dd bs=1M iflag=direct` — ⚠️**단일 스레드·readahead 없음이라 대역이 아니라 지연 측정에 가깝다** |
| 모델 저장소 총량 | **229 GB**(35개 모델, 2026-08-03 정리 후) | `du -sh` — blob 공유 0이라 모델 삭제 = 표시 크기 전액 회수 |

**RAM(31GB) < 모델 총량(229GB)** — 페이지 캐시에는 최근 쓴 것만 남는다. 캐시 상주는
**기회적이며 보장되지 않는다**.

> 2026-08-03 디스크 정리(103GB 회수 · 여유 220→316GB): Ollama 모델 3종 42GB(`phi4:14b`·
> `deepseek-r1:14b`=코드 배선 0 · `qwen3.6:35b-a3b`=heavy 기본값, 초대형은 AirLLM으로 이관) +
> aux 비전 사이드카 R&D 잔재 64GB(Qwen3-VL 32B/8B 가중치·전용 venv·GGUF) + 업그레이드 잔재 2GB.
> **실사용 판정 기법**: ext4가 `relatime`이라 blob의 atime이 "마지막으로 읽힌 날"을 준다
> (`stat -c %X`). 단 서비스 재기동 시 전수 스캔이 atime을 리셋하므로 관측 창을 먼저 확인할 것 —
> 이번엔 창이 4일뿐이라 **atime을 삭제 근거로 쓰지 않고 코드 배선 여부를 1차 근거로 삼았다**.

## 3. 적재 비용 — 상주가 꼭 필요한가

`llm_resident=false`(요청 시 탑재)로 전환한 뒤 실측:

| 구분 | TTFT | 총 소요 |
|------|-----:|--------:|
| 콜드(언로드 직후 첫 요청) | **2.5 ~ 3.9초** | 2.6 ~ 4.0초 |
| 웜(적재 상태) | **0.13초** | 0.23초 |

**계산으로 교차 검증**: 9.0GB ÷ 3.1GB/s ≈ 2.9초로 실측(2.5~3.9초)과 맞아떨어졌다.

> 🔴 **2026-08-03 정정**: 위 3.1GB/s는 `O_DIRECT` 단일 스레드 값이고, **커널 readahead가 붙는
> 일반 버퍼드 순차 읽기는 9.9GB/s**다(35GB 콜드 실측). 이 디스크는 **SK hynix Platinum P51 =
> PCIe 5.0**이다. Ollama 모델 적재가 2.5~3.9초인 것은 대역이 아니라 **적재 경로의 다른 비용**
> (mmap·검증·GPU 전송)이 지배하기 때문으로 보인다.
> **대역 기반 추정을 할 때는 접근 방식에 맞는 수치를 쓸 것** — 순차 대량 읽기면 9.9GB/s다.

> 🔑 **설계 결론**: 이 하드웨어에서 **상시 상주는 필수가 아니다.** 10.5GB를 24시간 붙잡아
> 얻는 것은 "유휴 후 첫 요청 2~4초"뿐이다. VRAM을 다른 용도(파인튜닝·배치 STT·이미지)에
> 쓸 수 있다면 그쪽 가치가 대개 더 크다.
>
> 페이지 캐시를 `vmtouch -l`로 고정하는 방안은 **권장하지 않는다** — 31GB 중 9GB를 회수 불가
> 상태로 묶어 OOM 위험을 만들면서 얻는 이득이 1~2초다. 지금은 27GB가 "회수 가능한 캐시"라
> 학습·배치가 필요한 만큼 가져다 쓸 수 있는 편이 낫다.

## 4. 설정 우선순위 함정 (반드시 확인할 것)

Ollama 실효 설정은 **두 곳**에서 온다. 유닛의 `EnvironmentFile=-/etc/default/ollama`가
systemd drop-in(`ollama.service.d/environment.conf`)을 **덮어쓴다**.

| 키 | drop-in | /etc/default/ollama | 실제 |
|----|---------|---------------------|------|
| `OLLAMA_KEEP_ALIVE` | 5m | ~~-1~~ → **5m**(2026-07-30 교정) | 5m |
| `OLLAMA_MAX_LOADED_MODELS` | 1 | ~~2~~ → **3** | **3** ⚠️ (2026-09-29 실측) |

- 2026-07-30 이전에는 `KEEP_ALIVE=-1`이 이겨 **어떤 요청이든 한 번 적재되면 영구 고정**됐다.
  앱의 예열만 꺼도 해결되지 않았고, 이 사실을 모른 채 앱만 들여다보면 원인을 못 찾는다.
- **2026-09-29 운영 결정 — 정본 = `/etc/default/ollama`**(admin-menu-settings-cleanup §7-3). drop-in의 중복 키를 걷어내고
  drop-in 전용 2키(`KV_CACHE_TYPE=q8_0`·`CONTEXT_LENGTH=8192`)를 옮긴다(실효값 불변 → Ollama 재시작 불필요).
  설정 파일과 drop-in 디렉터리는 root 소유로 두고, 앱 계정이 바꿀 수 없게 하십시오.
- **관리 콘솔(설정 › 모델·엔진)은 v2.125.54부터 이 표를 스스로 계산해 보여 준다** — `GET /api/ollama/perf`의 `effective`
  (키별 실제값·출처·가려진 값). GPU 서버에선 읽기 전용(파일이 root 소유)이고, 저장 시도는 409+이유. 화면에서 값을 바꾸는 기능은 없다.
- **`MAX_LOADED_MODELS`는 실제 3이다**(2026-09-29 기준 — 한때 2). 문서 여러 곳이 "MAX_LOADED=1 전제"로 쓰여 있으니
  (heavy tier의 축출·복원 설명 등) 재설계 시 실제값을 먼저 확인할 것.
- **거동으로 확인하는 법**: `/api/ps`의 `expires_at`이 `2318년`이면 `keep_alive=-1`,
  유한하면 정상 만료. `/proc/<pid>/environ`은 ollama가 root라 읽을 수 없다.

## 5. 상주 정책 — 선택지와 판단 기준

`core/llm_residency.py` · `GET|POST /api/models/residency`(무재배포 전환).

| 상황 | 권장 | 이유 |
|------|------|------|
| 대화형 트래픽이 상시 있고 VRAM 여유 있음 | **상주**(`resident:true`) | 첫 요청 지연 0 |
| 파인튜닝·대형 모델 실험 병행 | **요청 시 탑재**(현재) | 10.5GB 회수가 2~4초보다 가치 큼 |
| 파인튜닝 **직전** 확실히 비우기 | `POST /api/models/unload` | 실트래픽이 있으면 계속 적재된 것처럼 보인다 — 유휴 반납만 보장 |
| 콜드를 더 줄이고 싶음 | 기본 모델을 7b(4.7GB)로 | 콜드 절반 · 품질 67.5→60.5% 트레이드오프 |

**중요**: "요청 시 탑재"는 *유휴 시 반납*을 보장할 뿐 *항상 비어 있음*을 뜻하지 않는다.
appServer가 분당 ~16회 호출하므로 업무 시간에는 사실상 항상 웜이다.

## 6. 증설·재설계 시 참고

- **24GB+ 카드**로 가면 풀리는 것: large-v3 STT 동시 2~4, 비전+채팅 co-resident,
  heavy tier 상시화, 파인튜닝과 서빙 동시 운용. 현재 이 전부가 16GB 천장에 막혀 있다.
- **디스크는 병목이 아니다**(버퍼드 9.9GB/s · PCIe 5.0). 모델 교체가 잦은 설계(다중 소형 모델 스와핑)를
  택해도 적재 비용은 모델당 수 초 수준이다.
- **RAM 31GB**는 파인튜닝 데이터·CPU 오프로드에 여유가 크지 않다. 하이브리드 대형 모델
  구동(v2.118.0)의 실질 병목도 VRAM이 아니라 RAM이었다.
- 모델 저장소가 270GB까지 자랐다 — 디스크 여유(현재 219GB) 관리가 별도 축이다.

## 7. 모델 크기·메모리 산정식 (2026-08-04 · 자체 실측 보정)

> 새 모델 도입 검토 시 **여기서 계산하고 시작**한다. 계수는 이 서버 설치본에서 역산한 값이라
> 일반 표(4.5bit 등)보다 정확하다.

### 7.1 양자화별 실측 비트/가중치

`bits/weight = 파일크기(GB) × 8 ÷ 파라미터(B)` 로 설치본에서 역산:

| 모델 | 파라미터 | 양자화 | 크기 | **실측 bits/weight** |
|------|--------:|--------|-----:|--------------------:|
| qwen3-coder:30b | 30.5B | Q4_K_M | 18GB | **4.72** |
| qwen2.5:14b | 14.8B | Q4_K_M | 9.0GB | **4.86** |
| gpt-oss:20b | 20.9B | MXFP4 | 13GB | **4.98** |
| qwen3.6:35b-a3b | 36.0B | Q4_K_M | 23GB | **5.11** |
| gemma4:26b | 25.8B | Q4_K_M | 17GB | **5.27** |

→ **Q4_K_M 계획값 = 5.0 bits/weight**(범위 4.7~5.3). 임베딩·출력층 비중이 큰 모델일수록 높다.

| 양자화 | 계획 bits/weight | 비고 |
|--------|----------------:|------|
| Q8_0 | 8.5 | |
| Q6_K | 6.6 | |
| **Q4_K_M** | **5.0** | ⭐ 기본 선택 · 실측 보정 |
| IQ4_XS | 4.3 | |
| Q3_K_M | 3.9 | 품질 저하 체감 시작 |
| Q2_K | 2.9 | 대형 모델에서만 의미 |
| IQ1_M | 1.8 | 실험용 |

### 7.2 모델 파일 크기

```
크기(GB) = 파라미터(B) × bits/weight ÷ 8
```

**예**: Solar Open 2 250B Q4_K_M = `250 × 5.0 ÷ 8` = **156GB**

### 7.3 필요 RAM (Ollama/llama.cpp 하이브리드 MoE 오프로드)

```
RAM 필요 = 모델크기 − GPU적재분 − OS·앱 여유(10GB) 를 만족해야 하므로
RAM 필요 ≈ 모델크기 − GPU적재분 + 10GB
```

**GPU 적재분**(VRAM 16.3GB 기준):

| 조건 | GPU 적재 가능 | 산출 |
|------|-------------:|------|
| **exclusive**(상주 반납) | **~13GB** | 15.5 − KV·활성화 2.5 |
| **co-resident**(상주 14b 유지) | **~3.5GB** | 15.5 − 10.5(상주) − 1.5 |

> 실측 교차검증: `qwen3.6:35b-a3b`(23GB)를 co-resident로 돌릴 때 VRAM 10,357→15,035
> (GPU가 ~4.5GB 흡수) · 나머지 ~18.5GB는 RAM. 위 식과 부합.

**예**: Solar Open 2 Q4(156GB), exclusive → `156 − 13 + 10` = **필요 RAM 153GB**

### 7.4 KV 캐시 (긴 컨텍스트에서 지배적)

```
KV(GB) = 2 × 레이어수 × KV헤드 × head_dim × 컨텍스트 × 배치 × dtype바이트 ÷ 1e9
```

**예**: 80레이어 · GQA 8헤드 · head_dim 128 · 8K 컨텍스트 · 배치 1 · fp16
`2 × 80 × 8 × 128 × 8192 × 1 × 2 ÷ 1e9` = **2.7GB**

⚠️ **1M 컨텍스트 모델은 KV만 수백 GB**가 될 수 있다(위 예에서 컨텍스트 8K→1M이면 **335GB**).
"1M 지원"은 **그 컨텍스트를 실제로 쓸 수 있다는 뜻이 아니다** — 쓸 컨텍스트로 계산할 것.

### 7.5 🔴 하드웨어 제약 (이 서버)

| 제약 | 값 | 근거 |
|------|-----|------|
| **메인보드 RAM 상한** | **128 GiB** · 4 DIMM | `dmidecode -t 16` 실측 |
| 현재 장착 | DDR5-4800 16GB × 2 (**2슬롯 공석**) | |
| VRAM | 16.3GB (RTX 5080) | 교체 없이는 불변 |
| M.2 | 3슬롯 중 **2개 공석** | 디스크는 제약 아님 |

⚠️ **AM5는 4 DIMM 구성에서 메모리 속도가 크게 떨어진다**(4800 → 3600 MT/s 수준).
MoE 오프로드는 **RAM 대역이 곧 속도**라 체감 손실이 크다 — 2 DIMM 고용량이 4 DIMM보다 유리할 수 있다.

### 7.6 판정 — 어느 모델이 이 서버에 들어가나

`가능 = 모델크기 ≤ GPU적재분 + (RAM − 10GB)`

**현재(RAM 30GB, exclusive)**: `13 + 20` = **33GB 이하**
**128GB 업그레이드 시**: `13 + 118` = **131GB 이하**

| 모델 | Q4 크기 | 현재 30GB | 128GB 업그레이드 | 판정 |
|------|--------:|:---------:|:----------------:|------|
| qwen3.6:35b-a3b | 23GB | ✅ | ✅ | **현재 heavy tier** |
| gemma4:26b | 17GB | ✅ | ✅ | 미검증 후보 |
| gpt-oss-120b | ~73GB | ❌ | ✅ | |
| **Baichuan-M3-235B**(의료 특화) | ~147GB | ❌ | ❌ | Q3(115GB)면 아슬 |
| **Solar Open 2 250B** | **156GB** | ❌ | ❌ | **Q2_K(91GB)만 가능** |

→ **250B급을 Q4로 쓰려면 RAM 150GB+ = 이 메인보드로는 불가.** 플랫폼 교체가 필요하다.

### 7.7 도입 검토 체크리스트

1. **파라미터·활성 파라미터** 확인 — MoE면 활성이 속도를 좌우(3B 활성 → 58 tok/s 실측)
2. §7.2로 **파일 크기** 산정 → §7.3으로 **필요 RAM** 산정
3. §7.6 판정식으로 **현 하드웨어 가부**
4. **라이선스** 확인 — 계열 단위로 등급 매기지 말 것(Qwen2.5는 72B·3B만 별도 라이선스)
5. **thinking 모델 여부** — 맞으면 `think:false` 주입 경로 확인(미주입 시 **빈 응답**)
6. **dense vs MoE** — 대형 dense는 50~88초/문항(v2.118.0), MoE는 58 tok/s. **MoE만 실용적**
7. 투자 전 **grounded A/B로 현 구성 대비 우위 선입증**(`tier-b-ram-upgrade.plan.md` §5)
