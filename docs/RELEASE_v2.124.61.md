# Release v2.124.61 — 기본 LLM 상주 → 요청 시 탑재 (파인튜닝 VRAM 확보)

날짜: 2026-07-30 | 종류: feat(llm)/ops | 배포: GPU graceful HUP + **ollama 재시작**(NRestarts 0)

## 배경

파인튜닝 작업을 시작하려면 VRAM이 필요한데, 기본 모델 `qwen2.5:14b`가 **10.5GB를 상시 점유**
하고 있었다(16GB 중 64%). 운영자 지시로 **요청 시 탑재(on-demand)** 구조로 전환.

## 🔑 실제 상주 원인은 앱이 아니라 **엔진 기본값**이었다

앱의 예열(`_ensure_default_model`, `keep_alive=-1`)만 끄면 될 줄 알았는데, 끄고 나서도
**무트래픽 상태에서 10~20초 만에 모델이 다시 영구 고정**됐다(`expires_at=2318년`).

측정으로 좁힌 결과 — 앱 로그에 예열 기록이 없는데도 재적재 → 앱이 아님 →
**`/etc/default/ollama`에 `OLLAMA_KEEP_ALIVE=-1`**이 있었고, 이것이 systemd drop-in
(`environment.conf`의 `OLLAMA_KEEP_ALIVE=5m`)을 **덮어쓰고 있었다.**

즉 **어떤 요청이든 모델을 한 번 적재하면 영구 고정**되는 구조였다. 앱만 고쳤으면
"고쳤는데 왜 계속 물고 있지"로 끝날 뻔했다.

> ⚠️ 함께 발견: 같은 파일의 `OLLAMA_MAX_LOADED_MODELS=2`도 drop-in의 `1`을 덮어쓰고 있다.
> 문서(CLAUDE.md)는 **MAX_LOADED=1 전제**로 쓰여 있었으나 실제 동작은 2다. 이번엔 의미를
> 바꾸지 않기 위해 **건드리지 않았다** — 별도 판단 사안으로 기록.

## 1. 앱 — 예열을 정책으로 (`core/llm_residency.py`)

- `llm_resident`(기본 **True**=기존 동작) — 끄면 `_ensure_default_model()`·
  `GPUResourceManager._reload_llm()`이 **no-op**. 문자열 `"false"/"0"/"off"/"no"`도 수용.
- **`GET|POST /api/models/residency`**(admin) — 무재배포 전환. **전환 즉시 반영**한다
  (끄면 언로드, 켜면 예열) — 설정만 바꾸면 `keep_alive=-1`로 이미 물린 모델은 만료가 없어
  그대로 남기 때문.
- 회귀 `tests/test_llm_residency.py` 5.

## 2. 운영 — 엔진 기본값 교정

`/etc/default/ollama`: `OLLAMA_KEEP_ALIVE=-1` → **`5m`**(백업 `ollama.bak-20260730`).
`systemctl restart ollama`(NOPASSWD 범위) 후 검증.

## 3. 검증 (라이브)

| 확인 | 결과 |
|------|------|
| 전환 즉시 VRAM 반납 | 10,349 MiB → **15 MiB**(거의 전량 반납) |
| 재적재 만료 시각 | `2318년`(무기한) → **`+5분`**(유한) |
| 요청 시 탑재 | 정상 응답(3×7=21 · 5+8=13) |
| 무트래픽 재고정 | **없음**(앱 예열 no-op 확인) |
| 서비스 영향 | ollama NRestarts 0 · health 200 · 큐 0/0 · 실시간 STT 세션 0(저트래픽 창에 수행) |

## 3-b. 콜드/웜 응답 속도 실측 (전환 후)

전환의 유일한 대가는 **유휴 후 첫 요청의 적재 지연**이다. 실측(qwen2.5:14b·짧은 프롬프트):

| 구분 | TTFT(첫 토큰) | 총 소요 |
|------|--------------:|--------:|
| **콜드**(언로드 직후 첫 요청) | **2.5 ~ 3.9초** | 2.6 ~ 4.0초 |
| 웜(적재 상태) | **0.13초** | 0.23 ~ 0.29초 |
| 콜드(비스트리밍) | — | 3.13초 |
| 웜(비스트리밍) | — | 0.75초 |

- 즉 **첫 요청에 +2.4~3.8초**, 이후는 상주 때와 동일하다(웜 수치는 상주 모드와 같은 값).
- ⚠️**[정정]** 처음엔 "OS 페이지 캐시 덕분에 빠르고 캐시가 밀리면 훨씬 느려진다"고 적었으나,
  이어서 측정해 보니 **과장이었다**. 디스크가 **NVMe 3.1GB/s**(O_DIRECT=캐시 우회 실측)라
  9.0GB blob을 **캐시 없이 읽어도 ~2.9초**다. 캐시 히트(2.5초)와의 차이는 **1~2초 수준**.
  → 페이지 캐시는 있으면 좋은 것이지 **이 구조의 전제가 아니다**. 상세 → `docs/DESIGN_MODEL_SERVING.md`
- 적재 중 도착한 다른 요청도 함께 기다린다 → 유휴 뒤 버스트가 오면 그 버스트 전체가 한 번의
  지연을 공유한다.
- 실사용 트래픽(appServer ~16회/분)이 있으면 5분 만료에 걸리지 않아 **업무 시간에는 사실상
  항상 웜**이다. 콜드가 실제로 발생하는 구간은 이른 새벽·긴 유휴 뒤·파인튜닝으로 비운 직후다.

## 4. 운영 메모

- **실사용 트래픽이 있으면 모델은 사실상 계속 적재돼 있다**(appServer ~16회/분). 이는 정상 —
  "요청 시 탑재"는 *유휴 시 반납*을 보장할 뿐이다. 파인튜닝 직전에 확실히 비우려면
  **`POST /api/models/unload {"model":"qwen2.5:14b"}`**로 즉시 반납시킨 뒤 시작한다.
- 되돌리기: `POST /api/models/residency {"resident": true}` (+ 필요 시 `/etc/default/ollama`
  백업 복원). 콜드 첫 요청 지연이 부담되면 상주로 돌리면 된다.
- CPU-폴백 경보는 **모델 미상주 시 None**(v2.124.33 설계)이라 위양성 없음 — 실측 확인.
