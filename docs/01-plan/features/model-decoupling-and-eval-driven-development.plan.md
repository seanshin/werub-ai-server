### 🔴 초안 정정 — provider 게이트웨이는 **이미 있다**

초안은 "seam이 없다"고 썼으나 **그 부분이 틀렸다.** `core/llm_gateway.py`가 v2.51.0부터
있고 **라이브로 동작 중**이다(`/api/providers`·`/api/providers/models`·enable/disable/test).
OpenAI·Anthropic·Google·Groq·OpenRouter를 지원하고 `providers.json`으로 관리되며
모델명 접두(`gpt-`·`claude-`·`gemini-`)로 provider를 자동 해석한다.
한국어 후처리도 provider별로 갈라 둔다(`KOREAN_CHECK_BY_PROVIDER` — Claude·GPT는 검사 생략).

**현재 상태**: 외부 provider **전부 `enabled:false`·API 키 없음** → 실제 활성은 ollama뿐
(`/api/providers/models` = 40개 전부 ollama). **휴면 스캐폴딩**이다.

**그런데 이것이 이 기획의 문제를 풀지 못한다** — 층이 다르기 때문이다:

| | `llm_gateway`(기존) | 이 기획이 필요로 하는 것 |
|---|---|---|
| 정하는 것 | **모델명 → provider** | **task → 모델명** |
| 호출자가 넘기는 것 | `generate("qwen2.5:14b", …)` | `generate("medical_law.answer", …)` |
| 하드코딩 141회 | **그대로 남는다** | 사라진다 |
| 정책(`local_only`) | 없음 | fail-closed |

⇒ LLMGateway가 있어도 **호출자는 여전히 모델명을 손으로 적는다.** 그래서 141회가 남아 있다.
두 층은 겹치지 않는다 — 이 기획의 라우터가 모델명을 정하고, 필요하면 그것을 LLMGateway가
provider로 보낸다.

⇒ **결론은 바뀌지 않는다**: "어느 모델에 무엇을 물을 것인가"를 정하는 지점이 없다.
다만 **LiteLLM 판단에는 영향이 있다** — 다중 provider 추상화는 **이미 자체 구현이 있으므로**
LiteLLM의 상대 이득이 초안이 가정한 것보다 **더 작다**(§9-4d 결론을 강화한다).

📌 이 정정은 **내가 같은 이름의 파일을 덮어쓰다가** 발견했다(즉시 복구·라이브 무영향).
인벤토리를 grep 한 번으로 끝내고 "없다"고 단정한 대가다 —
**"없다"고 쓰기 전에 이름으로도 찾아볼 것.**

## 2. 논지

> **LiteLLM 도입 여부보다 "단일 진입점(seam)을 만드는 것"이 먼저다.**

seam 없이 LiteLLM만 넣으면 **56개 파일을 고치는 비용은 그대로**이고, 그 위에 의존성이 하나 늘 뿐이다.
seam이 있으면 그 뒤에 Ollama든 LiteLLM이든 사이드카든 **갈아끼울 수 있다**.

> **그리고 seam이 생겨도, 바꿔도 되는지 판정할 수단이 없으면 바꿀 수 없다.**

현재 판정 가능한 것은 의료법 40문항뿐이다. 나머지 11개 도메인(263 라우트)은
모델을 바꿨을 때 좋아졌는지 나빠졌는지 **알 방법이 없다**.

## 3. 🔴 선결 쟁점 — 프론티어 모델은 기술 결정이 아니다

디커플링은 기술 과제지만 **프론티어 모델을 실제로 쓰는 것은 정책·규제 결정**이다.
외부 API를 쓰는 순간 다음이 전부 걸린다:

| 걸리는 것 | 근거 |
|---|---|
| **PHI 비저장 확인서** | HIS에 서명 제공(`docs/01-plan/references/his-phi-nonstorage-confirmation.md`) |
| **식약처 LLM 규제 트랙** | 모델 카드·`digest` 고정·라우팅 API·`medical_pin_public_models` 가드 |
| **LICENSE 개인정보 고지** | "PHI 비저장·키 sha256" 명시 |
| **외부 API 0 기조** | `feedback_no_external_api` — "MIT 소스 자체 구축, 외부 의존 금지" |

🔑 **`digest`가 사라진다는 점을 특히 유의할 것.** 규제 트랙은 `GET /api/models/routing`으로
모델 **digest**(예: `7cdf5a0187d5`)를 통지하고, 트윈이 그것으로 재현성을 검증한다.
외부 API에는 digest가 없고 **공급자가 모델을 조용히 갱신**한다 —
"같은 모델명인데 어제와 다른 출력"이 규제상 문제가 된다.
⇒ 외부 provider를 쓰는 경로는 라우팅 API에서 **`digest: null` + `pinned: false`로 명시**하고,
규제 대상 기능에는 §6-1c의 `local_only`로 애초에 들어가지 못하게 한다.

### 3-1. 🔴 그리고 프론티어는 유료다 — 초안에 비용 축이 없었다

현재 전부 자체 호스팅이라 **한계비용이 0**이다. 외부 API로 나가는 순간 **호출량이 곧 비용**이다.

실측(2026-08-10, api_activity 35분 창 2,050건):

| 경로 | 35분 | 환산 |
|---|---:|---|
| `/api/chat` | **229건** | **6.5건/분 ≈ 9,400건/일** |
| `/api/medical-law/ask` | 40건 | ≈ 1,600건/일 |
| `/api/{prod,his}/{health,stats}` | 1,696건 | 대시보드 폴링(LLM 무관) |

토큰 규모: 큐 잡 1,459건 누적 **312,195토큰**(평균 214) ·
`chat_messages` 16,546건 **평균 9,147자**(RAG 컨텍스트 포함).

⇒ `/api/chat` 하나만 외부로 돌려도 **일 수천만 토큰 규모**다. 단가는 공급자·모델별로
다르므로 여기 적지 않는다 — **`jobs.tokens`·응답 `tokens`로 이미 토큰을 세고 있으므로,
전환 검토 시점에 실측 토큰 × 당시 단가로 산정한다**(추정치를 기획서에 박아두면 낡는다).

**설계에 반영할 것**

| 항목 | 내용 |
|---|---|
| 예산 상한 | task별 **일/월 토큰 상한**. 초과 시 로컬 모델로 강등(차단 아님) |
| 비용 관측 | Result의 `tokens`·`provider`를 `api_activity`에 적재 → `/metrics` 게이지 |
| 경보 | 기존 `_perf_alerts`에 합류(새 채널 만들지 않는다) |
| 우선 대상 | **저빈도·고가치** task부터(`/ask` 1,600건/일 < `/api/chat` 9,400건/일) |

⚠️ **트래픽이 큰 경로부터 옮기면 비용이 먼저 터진다.** 품질 이득이 가장 큰 곳이 아니라
**비용 대비 이득이 큰 곳**부터 본다.

⇒ **이 기획서는 "교체 가능한 구조"를 만드는 데까지만 범위를 잡는다.**
실제 프론티어 전환은 **의료 경로를 제외한 도메인**(story/novel/game/coding 등)부터가 현실적이고,
의료·PHI 경로 전환은 **별도 규제 검토 사안**으로 남긴다. 이 경계를 코드로 강제한다(Phase 1-c).

## 4. 평가 주도 개발(EDD) — 이미 하고 있는 것을 규율로 굳힌다

이 프로젝트는 **이미 EDD를 하고 있다**. 다만 암묵적이라 사람마다·날마다 흔들린다.
새 방법론을 도입하는 게 아니라 **이미 값을 증명한 절차를 문서화·자동화**하는 것이 목표다.

### 4-1. 실제로 작동한 사이클 (증거)

| 단계 | 08-10 무면허 벌칙 사례 |
|---|---|
| ① **통제군이 먼저 깨진다** | 스모크 `control[penalty-unlicensed]` 63/64 |
| ② **기준을 사전 등록** | "정답 벌칙 배제 0건 · 벌칙 근거 전멸 0건" |
| ③ **진단(측정)** | 부분 절제 → 꼬리부 0.6881 > 전문 0.6699 |
| ④ **처치 후보를 측정으로 배제** | 재청킹·재랭커·질의 재작성 전부 기각 |
| ⑤ **처치 → 재측정** | 오귀속 67% → 0% · 필수 신호 12/12 |
| ⑥ **통제군이 닫힌다** | 스모크 **64/64** |
| ⑦ **회귀로 고정** | `test_medlaw_paragraph_filter.py` 31 |

같은 날 **처치 하나는 기각됐다** — 형량 부기가 금지 신호를 6/12 → 12/12로 악화시켜
되돌렸다. **EDD의 값은 채택이 아니라 기각에서 나온다.**

### 4-2. 규율 (Phase 3의 게이트로 자동화할 대상)

| # | 규율 | 어기면 생기는 일(실제 사례) |
|---|---|---|
| R1 | **결함은 통제군으로 먼저 고정**하고 처치는 그다음 | 처치 효과를 읽을 기준이 없다 |
| R2 | **채택/기각 기준·노이즈 밴드를 측정 *전에* 등록** | 08-05 "45%→30% 개선" 보고 후 철회 |

| R8 | **추세 단절점을 명시** | 측정 교정을 성능 개선으로 오독 |

### 4-3. 새 기능·모델 변경의 표준 절차 (제안)

```
1) 통제군 케이스를 먼저 쓴다      → config/golden/<domain>.json
2) 기준을 등록한다                → 기획/이슈에 채택·기각 조건 + 노이즈 밴드
3) 구현
4) G1 스모크 → G2 골든셋 → G4 회귀 (수 분)
5) 변경이 LLM 출력에 닿으면 G3 배치 (도메인 단위)
6) 결과를 릴리즈 문서에 **기각 포함** 기록
```

⚠️ **R3은 모델 교체 A/B에는 쓸 수 없다** — 모델이 바뀌면 답변이 당연히 달라지므로
"답변 고정 재채점"이 성립하지 않는다. ⇒ **모델 A/B는 R2의 노이즈 밴드가 유일한 방어**다.
밴드 없이 모델을 비교하면 v2.124.78(N=8 품질 우위가 N=16에서 재현 실패)이 반복된다.

## 6. Phase 1 — LLM 호출 seam 확립 (LiteLLM 무관)

### 1-a. `core/model_router.py` 신설  ✅ **완료**(08-10)

provider 중립 인터페이스 하나. 첫 어댑터는 **현재 Ollama 경로 그대로**(동작 변경 0).

```
generate(task, messages|prompt, *,
         schema=None,          # 1-9 format 제약 디코딩 — 어댑터가 못 지키면 즉시 기각
         images=None,          # 1-4 data: 접두·WEBP 정규화는 seam 안에서
         tools=None,           # 1-3 tool_calls 양방향 변환
         ctx_hint=None,        # 1-1 요청별 num_ctx 산정 근거(추정 토큰)
         think=None,           # 1-5 capability 확인 후에만 전달
         keep_alive=None,      # 1-7 상주 정책 — 안 보내면 Ollama가 5분으로 재설정
         seed=None, temperature=None,   # 규제 트랙 재현성(트윈 S6)
         max_tokens=None,      # v2.110.1 num_predict 캡
         timeout=None, stream=False) -> Result
```

- `task`: `"medical_law_answer"` · `"quality_judge"` · `"story_polish"` 처럼 **역할 이름**.
  모델명이 아니다. 모델은 config가 정한다(`config/model_routing.json`).
- 반환은 **정규화된 Result**(text·tokens·model·**digest**·finish_reason·latency·`provider`).
  `digest`는 로컬만 채워지고 외부는 `None`이다(§3) — 소비자가 그것으로 분기할 수 있어야 한다.
- 실패는 예외가 아니라 Result에 실린다(기존 `_gen_failed` 규율 계승).

**경계를 분명히 한다 — seam이 하지 않는 것**

| 관심사 | 어디 | 왜 |
|---|---|---|
| 응답 캐시 | **seam 위**(호출자) | 캐시 키에 이미지·think·options가 들어가야 한다(v2.124.59). seam 안에 두면 task별 키 정책이 뭉개진다 |
| 큐/배치 | **seam 위** | 큐는 잡 수명주기이고 LLM 호출은 그 안의 한 단계 |
| 한국어 후처리 | **seam 위** | 1-6에서 내용을 지운 사고 — 후처리는 도메인이 정한다 |
| 노드 분산 | **seam 아래 아님**(직교) | `dispatch.run`은 capability 단위. seam은 "어느 모델", dispatch는 "어느 기계" |
| VRAM/스왑 | **seam 안** | `keep_alive`·상주 정책은 모델 선택과 붙어 있다 |

### 1-b. 모델명 하드코딩 141회 → config 이관

`task → model` 표를 config로 뺀다. 무재배포 전환 + `GET /api/models/routing`이 이미 있으므로
**규제 트랙의 "서빙 모델 실시간 조회" 계약을 그대로 유지**한다.

**task 이름 규약**(안 정하면 141개가 141개 task로 흩어진다):

```
<domain>.<role>        예) medical_law.answer · eval.faithfulness_judge
                           counseling.reply · korean.spellcheck · story.polish
```
- 등록되지 않은 task는 **기동 시 실패**(오타로 조용히 기본 모델을 타는 것 방지 — v2.124.62 선례)
- `GET /api/models/routing`이 **task 목록과 해석된 모델·digest·policy를 전부** 노출

### 1-f. 🔴 임베딩도 같은 축이다 (초안 누락)

`bge-m3`가 **32회 하드코딩**돼 있고 `client/rag.py`에 `embed_text`가 있다.
임베딩은 `generate`와 성질이 달라 **별도 seam**이 필요하다:

```
embed(task, texts, *, ctx=2048) -> list[vector]
```

⚠️ 그리고 **임베딩 모델 교체는 생성 모델 교체와 비용이 다르다** —
**전 코퍼스를 재색인해야 한다**. 선례가 있다: v2.124.8에서 거리 공간만 바꾸는 데도
12,686청크를 재구축했다(`scripts/migrate_medlaw_cosine.py`, 9.4초 — 저장 임베딩 재사용이라 빨랐다).
**차원이 바뀌면 재사용이 불가능해 임베딩을 다시 계산해야 한다**(medical_law 13,002 +
medical_pub 15,285 + werub_docs + edu_docs …).

⇒ **임베딩 모델은 `pinned`로 관리하고 교체는 마이그레이션 계획과 함께만.**
seam은 "바꿀 수 있게" 만들되 **바꾸기 쉬워 보이게 만들면 안 된다**.
`config/model_routing.json`의 임베딩 항목에 `requires_reindex: true`를 명시한다.

### 1-c. 🔴 경로 등급 강제

seam에 **`policy` 태그**를 둔다: `local_only` | `any`.
- 의료·PHI·규제 경로(`medical*`·`his*`·`dur*`·`medical_law*`)는 **`local_only`**
- 외부 provider 어댑터는 `local_only` task를 **거부**(fail-closed)

이러면 프론티어 전환이 의료 경로로 **번지지 않는다**. §3의 경계를 코드가 지킨다.

### 1-d. 이관 순서 (한 번에 56파일을 고치지 않는다)

| 단계 | 대상 | 스트리밍 | 근거 |
|---|---|---|---|
| 1 | `medical_law` **비스트리밍**(`/ask`) | ✗ | 평가 자산이 있는 유일 도메인 = **효과를 측정할 수 있다** |
| 2 | judge 2종(`faithfulness`·`llm_judge`) | ✗ | judge 고정(§8-a)의 전제 · 배치라 위험 낮음 |
| 3 | `medical_law` **스트리밍**(`/ask/stream`) | ✅ | 포맷 3갈래 중 자체 NDJSON 하나로 먼저 검증 |
| 4 | `counseling`·`writing`·`korean` | 혼합 | 골든셋 확보 후 |
| 5 | `orchestrator`(yield 25)·`novel`(11) | ✅ | **가장 나중** — tool_calls 증분 스트림 위험 |
| 6 | 나머지 | — | — |

⚠️ **1단계 이후 반드시 40문항 배치 + 스모크로 무변경 확인**. 동작이 바뀌면 이관이 아니라 변경이다.

**채택 기준(사전 등록)**: 각 단계 후 ① 스모크 64/64 유지 ② 해당 도메인 배치 지표가
노이즈 밴드 내 ③ 회귀 전건 통과 ④ 스트리밍 단계는 **TTFT p90이 기존 대비 +20% 이내**
(v2.104.0에서 6.5초 → 0.0016초로 고친 이력이 있어 회귀 시 체감이 크다).
하나라도 미달이면 되돌린다.

### 1-e. 롤백 경로

seam은 **config 토글로 우회 가능**해야 한다 — `model_router_enabled=false`면
기존 직접 호출 경로를 그대로 탄다. 이관 단계마다 **양 경로를 남기고**,
해당 도메인이 한 배치 주기(주 1회) 무사고를 통과한 뒤 구 경로를 제거한다.

⚠️ 양 경로 병존은 **코드 중복 비용**이 있다. 단계당 최대 2주로 제한하고,
기한 내 제거하지 못하면 그 단계는 실패로 본다(중복이 영구화되는 것이 최악).

### 2-b. 골든셋 스키마 (control_set 구조를 일반화)

이미 검증된 형태다 — 스모크가 이 구조로 **실결함을 잡았다**(무면허 벌칙 제90조 오귀속).

```json
{"id":"...", "domain":"medical_law|counseling|korean|...",
 "input":{...}, "signals":[...], "signals_any":[...],
 "clause":["정규식|대안"], "forbidden":[...],
 "note":"왜 이 케이스가 있는가 — 어떤 사고에서 나왔는가"}
```

🔑 **`note`에 유래를 적는 것이 핵심이다.** 이 프로젝트의 통제군은 전부
"과거에 실제로 깨졌던 것"에서 나왔고, 그래서 값이 있다.

### 2-c. 도메인별 확보 전략 — 전부 같은 방식일 수 없다

| 도메인 | 정답이 존재하는가 | 접근 |
|---|---|---|
| medical_law · dur · 약가/코드 | ✅ 법령·정본 DB | **결정적 대조**(이미 부분 구현) |
| coding | ✅ 실행 가능 | 테스트 통과 여부 |
| korean(맞춤법·문체) | ✅ 규칙 | 결정적 판정(이미 register/expert_referral 이관 선례) |
| counseling · story · novel · game | ❌ 정답 없음 | **금지 신호 중심**(위기 미감지·페르소나 붕괴·설정 모순) |
| vision · meeting(STT) | ✅ 부분 | 참조 전사·라벨 |

⚠️ **정답이 없는 도메인에 억지로 정답을 만들지 않는다.** counseling/story는

### 2-d. 🔴 골든셋은 낡는다 — 이 프로젝트에서는 특히

정본 데이터가 **계속 갱신된다**: 약가목록·대체조제 **월별** · 치료재료·DUR **7일** ·
의료법 코퍼스 **일별 스케줄러**. 법령이 개정되면
`signals:["10년"]` 같은 통제군이 **거짓 실패**하고, 그때 사람이 하는 판단은 대개
"통제군이 틀렸네" → 완화다. 그러면 R5가 무너진다.

**대응(설계에 포함)**

| 항목 | 처리 |
|---|---|
| 각 케이스에 `as_of` | 근거 판본·조회일 기록 |
| 각 케이스에 `source_ref` | 조문·고시 번호 — 개정 감지의 기준 |
| **개정 감지** | 코퍼스 스케줄러가 해당 조문 텍스트 변경을 감지하면 **골든셋을 실패가 아니라 `stale`로** 표시 |
| 실패 vs stale 구분 | `stale`은 **게이트를 막지 않고 사람에게 올린다** |

⚠️ 이 구분이 없으면 **정본 갱신 때마다 게이트가 오탐으로 울고**, 결국 게이트를 끄게 된다
(41일간 6,354건을 울린 `Worker Threads High`와 같은 결말).

### 2-e. 규모 목표와 비용 산술 (사전 등록)

도메인당 **통제군 5** + **회전 풀 10~15**.

| 항목 | 실측/추정 |
|---|---|
| 40문항 충실도 배치 | **약 25~30분**(08-10 실측) |
| 40문항 품질 배치 | 약 15~20분 |
| ⇒ 도메인당 20문항 | **약 20~25분**(충실도+품질) |
| 12개 도메인 전량 | **4~5시간** — 매일은 불가 |

⇒ **G1+G2(통제군)는 변경마다**(수 분), **G3(회전 풀)는 도메인 단위 주간 회전**.
하루 2도메인이면 6일에 한 바퀴 — 기존 `eval_pool`의 7일 회전 설계와 정합한다.

⚠️ **한 번에 다 만들지 않는다.** 도메인 하나를 끝까지(골든셋→러너→스모크 합류) 해보고
비용·효용을 재고 다음으로 간다. 첫 대상은 **counseling**(위기 감지 = 안전 직결, forbidden 명확).

## 8. Phase 3 — 자동 평가·게이트

### 3-a. judge 고정 (§1-3 해소)

**judge 모델을 피평가 모델과 분리하고 버전으로 고정**한다.
- `JUDGE_MODEL`을 config로 올리고 **judge 교체는 별도 릴리즈**로만
- eval.db에 이미 `judge_model` 컬럼이 있다 → **judge가 다르면 추세를 잇지 않는다**(단절점 표시)
- 모델 A/B 시 judge는 **반드시 동일**

⚠️ judge를 프론티어로 올리는 선택지도 있으나(품질↑) **PHI가 judge에 들어간다** → 의료 도메인은 불가.
비의료 도메인만 선택적 허용 검토.

### 3-b. 회귀 게이트

| 게이트 | 대상 | 기준 | 소요 |
|---|---|---|---|
| **G1 스모크** | 전 도메인 계약 | **기준선 대비 신규 실패 0** | 수 분 |
| **G2 골든셋** | 도메인별 통제군 | 〃 (forbidden 신규 발생 0) | 수 분 |
| **G3 배치** | 회전 풀 | 지표가 **사전 등록 노이즈 밴드** 내 | 도메인당 20~25분 |
| **G4 회귀** | 순수 함수 | 전건 통과(현행 1,419) | 약 2분 40초 |

#### 🔴 게이트를 "전건 통과"로 잡으면 실패한다 — 실제 사례

초안은 G1을 **"64/64 유지, 깨지면 배포 중단"**으로 잡았다. **이건 못 쓴다.**
08-06~08-10 **4일간 스모크는 63/64였다**(무면허 벌칙 오귀속). 그 기준이었다면
**나흘간 모든 배포가 막혔을 것**이고, 실제로 그 사이 v2.124.92·93·94가 나갔다.

게다가 통제군의 실패는 **확률적**이다 — 같은 질의를 12회 돌려 제90조가 6~8회 나왔다.
LLM 출력 게이트에 결정적 전건 통과를 요구하는 것은 원리적으로 성립하지 않는다.

**⇒ 기준을 "절대"가 아니라 "기준선 대비 신규"로 잡는다.**

| 규칙 | 내용 |
|---|---|
| **베이스라인 파일** | `config/gate_baseline.json` — 현재 알려진 실패 목록(id + 사유 + 등록일) |
| **차단 조건** | 베이스라인에 **없는** 실패가 생기면 차단 |
| **기존 실패** | 차단하지 않고 **보고만** — 통제군을 약화시키는 게 아니라 *알려진 상태로 관리* |
| **flaky 처리** | 확률적 항목은 `retries: N, need: K`(예: 3회 중 2회 통과) 명시 · 기본은 1회 |
| **베이스라인 등록** | **사람이 명시적으로** 추가하고 사유를 적는다. 자동 추가 금지 |
| **만료** | 등록 후 30일 경과 항목은 리포트에 ⚠️ 표시(방치 방지) |

🔑 이건 **R5(통제군 약화 금지)를 지키면서 게이트를 실용화하는 유일한 방법**이다.
"실패를 지우기"가 아니라 "실패를 알려진 것으로 등록하고, 새 실패만 막기"다.

⚠️ 베이스라인이 **커지기만 하면** 게이트는 죽는다. **베이스라인 항목 수를 지표로 추적**하고
증가 추세면 그 자체를 결함으로 본다(§13 S7).

🔑 **G3의 노이즈 밴드는 측정으로 정한다.** 무처치 재실행 R=3의 변동폭이 밴드다.
이 프로젝트는 이걸 몰라서 08-05에 "45%→30% 개선"을 보고했다가 철회했다
([[feedback_fix_the_measurement_first]]).

### 3-c. 자동화 복원 — 어디서 돌릴 것인가

야간 cron이 중단된 상태다(운영 결정, v2.124.80). 현 crontab은 `health_check.sh`·`watchdog.sh`뿐.

⚠️ **`git push` 훅은 안 된다.** 배포는 로컬 push가 아니라 **GPU에서 `git pull` + graceful HUP**이다
(`DEVELOPER_GUIDE §3`). 게이트는 **모델이 있는 기계에서** 돌아야 한다.

**배선안**: 배포 절차의 마지막 단계로 넣는다.

```
GPU:  git pull → dry-run(import) → 회귀(G4) → HUP → **G1 스모크 + G2 골든셋**
                                                      └ 신규 실패 있으면 비-0 종료
주간: G3 배치(도메인 회전) — cron 또는 수동
```

- 산출물은 `eval.db`/`gate_runs`에 적재하고 **직전 결과와 diff**
- 실패 통지는 **기존 `_perf_alerts` 채널에 합류**한다(Slack/Discord/webhook이 이미 있다).
  새 알림 채널을 만들지 않는다 — 채널이 늘면 아무도 안 본다.
- G3는 GPU를 20~25분 점유하므로 **HIS 외래 피크(09~11·14~16) 회피**(운영 합의 기록 있음).

⚠️ **게이트가 배포를 막는 순간 사람은 게이트를 끈다.** 그래서 §8-3b의 "신규 실패만 차단"이
전제이고, 그마저도 **긴급 배포용 우회 플래그**(`--skip-gates` + 사유 로깅)를 둔다.
우회를 막는 게 아니라 **우회한 사실이 남게** 하는 것이 목적이다.

## 9. Phase 4 — LiteLLM (조건부·seam 뒤)

**seam(Phase 1)이 서고 게이트(Phase 3)가 돌기 전에는 착수하지 않는다.**

### 4-0. 🔴 전수 감사 결과 — 신규 이득이 거의 없다 (08-10 추가)

초안은 LiteLLM의 이득을 "provider 다수·재시도·폴백·비용 추적"으로 적었다.
**전수 감사 결과 그 대부분이 이미 자체 구현으로 있다**(정본 `docs/DESIGN_LLM_ABSTRACTION.md`).

| LiteLLM이 주는 것 | 현황 | 신규 이득 |
|---|---|---|
| 다중 provider 통합 | `core/llm_gateway.py`(OpenAI·Anthropic·Google·Groq·OpenRouter) | ❌ |
| OpenAI 포맷 통일 | `routes/openai_compat.py`(SSE·tool_calls·num_ctx 주입) | ❌ |
| 재시도·타임아웃·폴백 | `core/llm_resilience.py`(적응형 타임아웃·서킷 브레이커·요청 병합, **6파일 활성**) | ❌ |
| 모델 라우팅 | `routes/gateway.py`(복잡도)·`core/medical_router.py`(결정적) | ❌ |
| 비용·토큰 추적 | `jobs.tokens`·`api_activity` | 🟡 부분 |

⇒ **실질 신규 이득은 "비용 대시보드" 정도**이고, 대가는 **큰 의존성 트리 + 11계약 재검증**이다.

🔑 그런데 추상화가 여섯 층이나 있는데도 **모델명 하드코딩 141회가 남아 있다.**
이유는 **모든 층이 "모델명을 이미 아는 상태"에서 시작**하기 때문이다 —
호출자가 `generate("qwen2.5:14b", …)`라고 적으면 그 뒤가 아무리 정교해도 모델명은 박힌 채다.
`model_router`가 채우는 자리가 정확히 그 앞이다.

### 4-a. 무엇을 얻는가

- provider 다수(프론티어 포함)를 **어댑터 1개**로
- 재시도·타임아웃·비용 추적·폴백 체인이 기성품
- OpenAI 포맷 통일 → `routes/openai_compat.py`(17회 호출)와 개념 일치

### 4-b. 무엇을 잃을 수 있는가 — **채택 게이트**

Phase 0-3에서 고정한 11개 계약을 LiteLLM Ollama 경로가 **실측으로** 통과해야 한다.
문서를 근거로 채택하지 않는다.

| # | 검증 항목 | 미통과 시 |
|---|---|---|
| V1 | `options.num_ctx` 요청별 전달 | 🔴 **즉시 기각**(무성 절단 재발) |
| V2 | `format`(JSON 스키마) 제약 디코딩 | 🔴 **즉시 기각**(구조화 출력 전 경로 붕괴) |
| V3 | `keep_alive` 전달 | 상주 정책 수동 보완 |
| V4 | 이미지 base64 경로 | 어댑터에서 정규화 |
| V5 | `think` / capability | 어댑터에서 게이트 |
| V6 | 스트리밍 청크 형태 | SSE 변환 유지 |
| V7 | 지연 오버헤드 | p95 **+50ms 이내** |

### 4-c. 라이선스·의존성

- 오픈소스 SDK는 MIT로 알려져 있으나 **엔터프라이즈 계층은 별도 조건** →
  `LICENSE`의 제3자 구성요소 표에 **등급 명시 필수**(v2.124.78에서 NC 모델 누락 사고 있었음)
- 의존성 트리가 크다 → **SDK만 쓰고 proxy 서버는 도입하지 않는 안**을 기본으로

### 4-c-1. 검증은 새로 만들지 않는다

V1~V7은 **Phase 0-3에서 만든 11계약 테스트를 어댑터만 바꿔 재실행**하는 것이다.
LiteLLM 전용 검증 하네스를 따로 만들지 않는다 — 그러면 두 하네스가 갈라진다.

```
pytest tests/test_llm_adapter_contract.py --adapter=ollama    # 기준선
pytest tests/test_llm_adapter_contract.py --adapter=litellm   # 후보
```
⇒ **어댑터 계약 테스트를 파라미터화**해서 만들어 둔다(Phase 0-3 설계에 반영).

### 4-d. 비채택 시 대안

seam이 있으면 LiteLLM 없이도 어댑터를 직접 쓸 수 있다.
현재 필요한 provider가 **Ollama 하나**라면 **LiteLLM은 지금 이득이 없다** — Phase 1만으로 충분하다.
⇒ **채택 트리거: 두 번째 provider가 실제로 필요해질 때.**

📌 **솔직한 결론**: 이 기획서의 질문은 "LiteLLM을 쓸 것인가"였지만,
측정 결과 **지금 답은 '아직 아니다'** 이다. 병목은 provider 추상화가 아니라
**56파일에 흩어진 호출과 판정 수단의 부재**다. LiteLLM은 그 둘을 해결하지 못한다.

## 부록 A — 이 기획서가 지키려는 규율

이 프로젝트가 반복해서 배운 것들이며, 위 Phase 설계의 근거다.

- **측정 선행** — 처치 설계 전에 지표가 옳은지 확인 ([[feedback_fix_the_measurement_first]])
- **채택/기각 기준을 측정 *전에* 못 박는다** — 나중에 정하면 결과에 맞춰 기준이 움직인다
- **실물로 잰다** — 문서·작은 모델·다른 측정법에서 외삽 금지 ([[feedback_measure_the_real_thing]])
- **한 곳에서 고친 결함은 같은 클래스 전 경로에 적용** (v2.124.65 → .92 → .93)
- **효과 미확인 처치는 남기지 않는다** (v2.124.63)
- **통제군을 약화시키지 않는다** — 스모크가 실패하면 실패인 채로 둔다
- **완화 방향 변경은 통제군을 함께 고정한다** (v2.124.74·88·94)
