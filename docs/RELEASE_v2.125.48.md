# v2.125.48 — 상주 모델 복원 유예 (1차) + health_check 스왑 경고 상태 전이

기준 v2.125.47 · 출처 = 2026-09-28 배치 작업 전수 검토

⚠️ **이 릴리즈의 1차 처치는 사전 등록 기준에 미달했다**(적재 125→99, 기준 ≤40). 원인과 보완은
`RELEASE_v2.125.49.md`. 이 문서는 결함 발견·1차 처치·실패 기록을 남긴다.

## 1. 발견 — 평가 배치 "591회/시간 적재"의 정체

- 큐 워커는 놀 때 2초마다 `_ensure_default_model()`을 불러 상주 모델(14b)이 `/api/ps`에 없으면
  **즉시** 재적재했다.
- 16GB VRAM에 14b(9.9GB)와 7b가 함께 못 올라간다 → 평가 교차검증(7b를 주장×청크만큼 연속
  호출)의 **호출 사이 틈마다 14b가 끼어들어** 7b를 내쫓고, 다음 7b 호출이 다시 14b를 내쫓았다.
- 기준선(09-28 09:21~09:30 평가 배치 10문항·8.6분): Ollama 적재 **125회**(14b 62·7b 63),
  앱 예열 로그 **63회** ⇒ 14b 적재가 거의 전부 예열이었다.
- 운영 경로도 같은 영향: 다른 모델을 연달아 쓰는 흐름(상담 2단·비전·의료 모델)마다 14b가 끼어든다.
- ⚠️ 정정: 처음엔 `MAX_LOADED=1`로 설명했으나 유효 설정은 **3**(`/etc/default/ollama`가 drop-in의
  1을 덮음) — 병목은 개수가 아니라 **VRAM**. 결론(예열이 끼어든다)은 불변.

## 2. 1차 처치

`core/llm_residency.restore_due`: 다른 모델이 **쓰이는 동안**(ps의 `expires_at`이 전진하는 동안)은
복원하지 않고, 마지막 활동 후 유예(config `resident_restore_grace_s`, 기본 30s) 뒤 복원.
**아무 모델도 없으면 즉시 복원**(← 이것이 결함이었다, §3).

## 3. 측정 — 기준 미달

| 적재 | 125 | **99** | ≤40 ❌ |
| 예열 | 63 | 50 | |

타임라인 판독: **7b 적재 시작 ~0.3초 뒤마다 예열**이 났다 — 교체 중 14b가 내려가고 7b가 아직
안 올라온 **빈 순간**을 "아무도 안 씀 → 즉시 복원"으로 봤다. 배치 첫 3분은 스래싱이 없었다
(유예 자체는 작동). → v2.125.49에서 빈 상태도 유예 대상으로.

## 4. health_check 스왑 경고

`scripts/health_check.sh`가 스왑 ≥80%면 **5분마다** WARN을 써서 `health_check.log`에 **4,936줄**
(원인은 동거 스택·운영자 항목 — 조치 불가 반복이 다른 경고를 묻는다). → **진입·해소 때만** +
높은 상태 지속 시 **1시간마다 1줄**(상태 파일 `logs/.health_check_swap_state`).
