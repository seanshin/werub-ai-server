# 서빙 모드 — 상주 모델 운영 정책

> 2026-08-04 신설 · 실측 기반 · 전환은 API 1회(무재배포·즉시 반영)
> 관련: `docs/DESIGN_MODEL_SERVING.md`(VRAM 예산·산식) · `core/llm_residency.py` · `routes/heavy.py`

## 0. 전제 — 하드웨어와 제약

| 자원 | 값 |
|---|---|
| VRAM | 16.3GB (RTX 5080) |
| RAM | 30GB · swap 8GB |
| `OLLAMA_MAX_LOADED_MODELS` | **3** (2026-08-04 상향) |
| `OLLAMA_KEEP_ALIVE` | 5m (요청별 오버라이드 가능) |

⚠️ **`keep_alive`는 축출을 막지 못한다.** `-1`(무기한)로 고정해도 **VRAM·슬롯이 부족하면 축출**된다
(7b·3b·35b 모두 실증). 상주를 보장하는 것은 **모델 크기 + 슬롯 수**뿐이다.

## 1. 모드 정의

전환은 두 값의 조합이다 — `llm_resident`(bool) + `llm_resident_model`(문자열).

```bash
POST /api/models/residency {"resident": true, "model": "<모델>"}    # 켜기·교체
POST /api/models/residency {"resident": false}                      # 끄기(즉시 언로드)
GET  /api/models/residency                                          # 현재 모드 조회
```

| 모드 | 상주 모델 | VRAM 점유 | 남는 VRAM | 용도 |
|---|---|---:|---:|---|
| **quality** | `qwen3.6:35b-a3b` | 14.3GB | **2.0GB** | RAG·분류 **전용** 워크로드에서만(§3-b) |
| **balanced**(기본) | `qwen2.5:14b` | 10.5GB | 5.8GB | 범용 — **혼합 트래픽 환경의 기본** |
| **light** | `qwen2.5:3b` | 2.4GB | 13.9GB | 분류 전용 최소 점유 |
| **off** | 없음 | 0GB | 16.3GB | 파인튜닝·대형 배치 |

## 2. 실측 성능 (2026-08-04)

### 지연 — **출력 길이에 따라 완전히 달라진다**

| 작업 | `qwen3.6:35b-a3b` | `qwen2.5:14b` |
|---|---:|---:|
| 짧은 분류(JSON ~100토큰) | **0.77s** | 0.4s |
| RAG 답변(~400자) | 25s | — |
| 일반 채팅(~480자) | **30s** | **6.1s** |
| 콜드 로드 | 12.1s | ~3s |

35b는 **CPU 오프로드 40%**(23.8GB 중 VRAM 14.3GB) 상태로 동작한다. MoE(활성 8/256 전문가)라
**짧은 출력에서는 거의 손해가 없고**, 긴 생성에서 비용이 드러난다.

> 📌 dense와 비교: 같은 날 EXAONE 4.0 32B(dense·19GB)는 **64s/건**이었다. 같은 VRAM 초과라도
> **MoE는 감당하고 dense는 못 한다.** 16GB 초과 모델을 검토할 땐 MoE 여부를 먼저 볼 것.

### 품질 — **근거 유무가 갈림길**

| 경로 | 35b | 14b |
|---|---|---|
| **RAG(근거 있음)** | ✅ 제15조① **단서까지 정확 인용** | — |
| **근거 없는 일반 질의** | 🔴 "보존기간 5년"(**오답**) + `의료기관의 진료기록 보관에 관한 규정`(**존재하지 않는 규정 창작**) | ✅ "10년"(정답) |
| 스팸 분류 16건 | 검출 100% · 오탐 0% · bec/spam 구분 ✅ | 검출 100% · 오탐 0% ✅ |

> 🔴 **35b는 근거가 있을 때 강하고, 없을 때 오히려 창작한다.** quality 모드에서 근거 없는
> 일반 채팅을 많이 태우면 품질이 **떨어질 수 있다.** RAG·분류 중심 워크로드에 맞는 모드다.

### 🔴 정정 (2026-08-18) — **근거가 있을 때도 14b와 차이가 없다**

v2.124.76이 낸 *"품질은 qwen3.6 유의 우세(p=0.039)"* 가 **N=40에서 재현되지 않았다.**
같은 하네스(`scripts/eval_hybrid_ab_qwen36_full.py`)·같은 grounded 의료법 질의로 재측정:

| | `qwen2.5:14b` 상주 | `qwen3.6:35b-a3b` heavy |
|---|---:|---:|
| 충실도 | 0.971 | 0.987 · **부호검정 3승 3패 · 동률 34 · p=1.000** |
| 품질 | 4.333 | 4.325 · **부호검정 15승 15패 · 동률 9 · p=1.000** |
| 환각 | 3/40 | 3/40 |
| **생성 중앙** | **5.2s** | **28.7s (5.52배)** · 35b가 빠른 문항 **0/40** |

📌 **N을 16 → 40으로 늘리자 우위가 사라졌다.** v2.124.78과 같은 패턴이다(EXAONE이 N=8에서
우세해 보이다 N=16에서 p=1.000으로 재현 실패). 그때 남긴 규율이 *"heavy 후보는 N≥16으로 시작"*
이었는데 **16도 부족했다.**

⚠️ **평균만 보면 안 된다** — 충실도 평균은 0.971 vs 0.987로 35b가 나아 보이지만 쌍 비교는 3승 3패다.
34문항이 동률이고 평균 차는 소수 문항의 **크기**에서 나온 것이지 **방향**이 아니다.

⇒ **근거 기반 경로(`/ask` 등)에서 heavy를 쓸 근거가 없다.** 5.5배 비용에 대응하는 이득이
이 과제에서는 측정되지 않는다. heavy tier 자체는 on-demand라 유지 비용이 0이지만,
**"품질이 더 좋다"를 전제로 배선하지 말 것.**

⚠️ 이 측정은 **의료법 grounded 독해**였다. **창작·장문 축은 2026-08-25 G1으로 쟀다(N=40) → 현상 유지**:
품질 쌍별 15:12 동률13 **p=0.70**(A-A 노이즈 47.5% 안이라 차이 없음) · 지시 신호 준수는 오히려
상주 14b가 우세(97.5% vs 87.5%) · heavy 3.1배 느림 · 사고 누출 0. ⇒ grounded 무승부에 이어
**창작에서도 heavy 우위 근거 없음**. 정본 `docs/01-plan/features/heavy-creative-longform-eval.plan.md`·
원자료 `docs/01-plan/references/heavy-creative-eval-result.json`. 비전 축은 여전히 미측정이다.

## 3. quality 모드의 운영 주의

### 공존 가능한 것

```
qwen3.6:35b-a3b  14.3GB  📌상주
bge-m3            0.7GB   ← RAG 임베딩, 공존 확인됨
────────────────────────
합계 15.0GB / 16.3GB
```

### 공존 불가능한 것 — **남은 여유가 2.0GB뿐**

`qwen2.5:14b`(10.5GB)·`med42`(8.5GB)·`medgemma:27b`(17GB) 등은 들어갈 자리가 없다.
**이 모델들을 부르면 35b가 축출되고, 되돌아올 때 12초 콜드 로드를 문다.**

⚠️ 야간 평가 배치는 2026-08-04 운영 결정으로 중단됐다(judge가 14b라 같은 충돌이 있었다).

## 3-b. 🔴 quality 모드는 **실트래픽 구성에 종속된다** (2026-08-04 실증)

quality 모드를 켠 상태에서 실사용 트래픽이 들어오자 **35b가 계속 축출됐다.**

```
ollama: "model predicted to exceed available memory, evicting"
  predicted 11.4GiB(qwen2.5:14b, num_ctx 16384) · available 1.8GiB
  predicted 22.5GiB(qwen3.6:35b-a3b)            · available 5.1GiB
```

원인은 **채팅 경로와 상주 모델이 서로 다른 모델을 요구**하는 것이다.

| | 모델 |
|---|---|
| `/api/chat`(외부 node 클라이언트, 10분간 **68건**) | `default_model` = `qwen2.5:14b` |
| 상주 | `llm_resident_model` = `qwen3.6:35b-a3b` |

여유 2.0GB에서 둘은 공존할 수 없다 → 요청마다 상호 축출 → `/ask` 45초(콜드), 실트래픽도 콜드.

> 🔑 **상주 모델은 "가장 좋은 모델"이 아니라 "트래픽이 실제로 쓰는 모델"이어야 한다.**
> 품질이 좋아도 트래픽이 다른 모델을 부르면 상주는 스왑 비용만 만든다.

### quality 모드를 실제로 쓰려면

- `default_model`도 35b로 통일 — ⚠️ 채팅은 **근거 없는 경로**이고, 35b는 근거가 없으면
  창작한다(실측: "보존기간 5년" 오답 + 존재하지 않는 규정). **권장하지 않는다.**
- 또는 RAG·분류 전용 인스턴스로 분리(현재 GPU 1대라 불가)

⇒ **혼합 트래픽 환경에서는 `balanced`가 기본이다.** 2026-08-04 quality 시도 후 복귀했다.

## 4. 모드 선택 지침

| 상황 | 모드 |
|---|---|
| RAG 자문·스팸 분류 **전용**(일반 채팅 트래픽 없음) | **quality** |
| 일반 채팅·다모델 혼합 트래픽 | **balanced** |
| 스팸 분류만 상주 보장, 나머지는 여유 확보 | **light** |
| 파인튜닝·대형 모델 실험 | **off** |

## 5. 되돌리기

```bash
POST /api/models/residency {"resident": true,  "model": "qwen2.5:14b"}   # balanced
POST /api/models/residency {"resident": true,  "model": "qwen2.5:3b"}    # light
POST /api/models/residency {"resident": false}                            # off
```

전부 **config 변경뿐**이며 재배포·재기동이 없다. 모델 교체 시 이전 상주는 자동 반납된다.
