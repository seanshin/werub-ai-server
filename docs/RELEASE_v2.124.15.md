## 요약

운영자가 data.go.kr **치료재료정보조회서비스 활용신청**(자동승인)을 완료해, v2.118.5부터
휴면 상태였던 `core/hira_mcat_sync.py`가 가동됐습니다. 라이브 첫 수집에서 **API 실동작이
모듈 가정과 달랐던 지점 2건을 실측으로 확정하고 수정**해 **91,211건 전량 적재**에 성공했습니다.

**청구 코드 해석 3축 완성** — 수가(TARIFF 7,138)·약가(DRUG 21,959)·**치료재료(MATERIAL
91,211)**. ERP 사전심사의 치료재료 코드→notice_type 자동해석이 활성화됐습니다.

## 실측으로 확정한 API 특성 2건 (모듈 수정)

### ① 검색 조건 필수 — 무조건 전체조회는 0건 (커밋 46b0720)

기존 구현은 `pageNo`+`numOfRows`만 보내는 전체조회였는데, 이 서비스는 **검색 조건이
없으면 `totalCount=0`**을 반환합니다(오류가 아니라 정상 응답 + 빈 목록이라 조용히
실패). 파라미터 후보 10종을 프로빙해 실동작을 확정:

| 파라미터 | 결과 |
|---|---|
| (없음) | totalCount **0** |
| `itmNm`(품목명) | 동작 — **SQL LIKE 패스스루**(부분일치·접두/접미 무관) |
| `impEntpNm`(수입업체명) | 동작 |
| `mcatCd`(재료대코드)·`mdivCd`(중분류) | 정확일치만 동작 |
| `mtrNm`·`prdNm`·`ldivCd`·`payTpNm` 등 | 0건(미지원) |

`itmNm`이 LIKE로 전달되는 성질을 이용해 **`itmNm="%"` 와일드카드 = 전 품목 91,211건**
수집 경로를 확보했습니다(공백 `" "`은 75,078건 부분집합, 빈 문자열은 0건).

### ② 특정 페이지가 1000행에서만 410 Gone (커밋 후속 2건)

92페이지 장주행 중 **page 60에서만 410 Gone**이 재현됐습니다(59·61페이지는 400KB대
정상). 재시도·간격 확대(0.05s→0.2s)로도 해소되지 않아 경계를 좁힌 결과:

- 같은 오프셋 구간(59,000~60,000)을 **100행 단위 10개로 나누면 전부 200** — 즉
  **레코드 결함·스로틀이 아니라 그 페이지의 1000행 응답이 게이트웨이 처리 한계를 초과**.
- fix = `_fetch_page_retry`에 **세분화 폴백**(재시도 소진 시 `SUB_DIV=10`배로 분할·재귀
  중첩 허용) → 데이터 **누락 0**으로 통과. 비재시도 상태(404 등)는 즉시 전파 불변,
  403/DENIED의 `PermissionError` 휴면 경로도 불변.
