# Release v2.124.66 — 큐 대기 시간 노출 (조용한 직렬화 가시화)

날짜: 2026-07-30 | 종류: feat(chat/observability) | 배포: GPU graceful HUP(NRestarts 0)

## 배경 — Cerno 동시성 실측이 드러낸 관측성 공백

Cerno가 `06_동시성_실측.md`로 단일 키 동시 요청을 측정했다. 우리 A-1 회신(`max_per_user=1`,
버킷 = API 키 sha256)이 사실임을 확인했고, 그 과정에서 **우리 쪽 문제**가 드러났다:

> *"429는 발생하지 않았다 — 대기열 20·대기 60초 안에 들어오므로 **거부가 아니라 조용히
> 느려진다.** 이게 더 나쁘다. 장애로 보이지 않아 원인을 찾기 어렵다."*

실측 기울기 **≈1.16초/요청**. 동시 3명이면 마지막 응답 5.4초로 p95 목표를 넘긴다.
그런데 호출자에게는 "그냥 느린 서버"로만 보였다 — **서버는 대기 시간을 알고 있으면서
응답에 싣지 않았다**(`_chat_queue.acquire()`가 `waited`를 돌려주는데 버려짐).

## 수정

`core/queue_signal.py` 신설 — `/api/chat` **스트리밍·비스트리밍 양쪽**에 헤더 부착:

| 헤더 | 의미 |
|------|------|
| `X-Queue-Waited-Ms` | 대기열에서 기다린 시간(ms). **0도 명시**한다(헤더 부재와 "대기 없음"을 구분) |
| `X-Queue-Position` | 대기 진입 시 순번(대기했을 때만) |
| `X-Queue-Active` | 응답 시점 전체 활성 요청 수 |

부가 정보라 **기존 응답 계약은 불변**이다.

## 부수 — 죽어 있던 헤더 하나

첫 구현 후 라이브에서 보니 `X-Queue-Position`이 **항상 비어 있었다.** `ChatFairQueue.acquire()`가
대기 후 성공할 때 `return True, True, 0, 0`으로 **순번을 버리고** 있었기 때문이다.
진입 시 순번을 그대로 돌려주도록 고쳤다(429 경로만 쓰던 값이라 영향 없음).

**만들고 나서 실제로 호출해 보지 않았으면 빈 헤더를 내보내며 "노출했다"고 할 뻔했다.**

알람할 수 있다.
